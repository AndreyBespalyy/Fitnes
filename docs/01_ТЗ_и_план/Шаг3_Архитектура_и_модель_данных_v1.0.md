# Что решено на этом шаге

Документ уточняет раздел 5 ТЗ v2.1 до уровня, с которого можно писать код (шаг 4, каркас платформы). Учтены ответы от 10.11.2026:

- доступ к системе пока по IP-адресу 144.31.107.204, без домена;
- сотрудники входят по логину и паролю;
- лимиты управляющего утверждены: возврат до 15 000 ₽, скидка до 15 %, расход до 50 000 ₽;
- два клуба на разных моделях продаж: «Центр» (абонементы на срок) и «Север» (подписка), модель задаётся при создании клуба и меняется администратором.

# 1. Технологический стек пилота

Выбор сделан так, чтобы один язык закрывал сервер, веб и будущее мобильное приложение, а весь пилот поднимался на одном сервере.

| Область | Решение | Почему |
|---|---|---|
| Язык | TypeScript везде (сервер, веб, мобильное) | Один язык и общие типы данных между сервером и интерфейсом, меньше ошибок на стыках |
| Сервер (API) | Node.js 22 LTS + NestJS, модульный монолит | Чёткие модули-домены, внедрение зависимостей, готовые механизмы прав и валидации |
| База данных | PostgreSQL 16 + pgvector | Транзакции для денег, построчная изоляция клубов, векторный поиск для ИИ без отдельной системы |
| Доступ к БД | Drizzle ORM + SQL-миграции в репозитории | Прозрачный SQL, миграции версионируются вместе с кодом |
| Очереди и события | Таблица outbox в PostgreSQL + Redis (BullMQ) для фоновых задач | На пилоте достаточно; переход на RabbitMQ или Kafka без смены доменного кода |
| Веб-интерфейс | React + Vite, PWA (устанавливается на телефон как приложение) | Экран менеджера на телефоне уже на пилоте; дизайн берём из прототипа шага 2 |
| Мобильное приложение | React Native (Этап 1Д), переиспользует логику и типы веба | Одна команда, одна кодовая база для iOS и Android |
| Файлы | MinIO (S3-совместимое хранилище) на том же сервере | Договоры, записи звонков, файлы импорта; позже переносится в облачный S3 без правок кода |
| Аналитика | Витрины (материализованные представления) в PostgreSQL | На объёмах двух клубов ClickHouse не нужен; добавляется на Этапе 2 |
| Веб-сервер | Caddy: HTTPS, сжатие, раздача фронтенда | Автоматические сертификаты; см. раздел 6 про HTTPS по IP |
| Развёртывание | Docker Compose, сборка образов в GitHub Actions | Один файл описывает всю систему, обновление одной командой, откат на предыдущий образ |
| Наблюдаемость | Структурированные логи (pino), метрики Prometheus, Grafana, проверка здоровья | Видно ошибки интеграций и время ответа |
| ИИ-контур | Отдельный сервис (Python, vLLM + Whisper) на GPU-сервере, подключается на этапе ИИ-0 | Сервер пилота без GPU; API ИИ закладывается сразу, чтобы потом только «включить» |

## 2.2. Схема компонентов пилота

```
 Телефон менеджера (PWA) ─┐
 Браузер руководителей ───┤        Сервер 144.31.107.204 (Docker Compose)
 Экран ресепшн ───────────┼──HTTPS──► Caddy ──► api (NestJS) ──► PostgreSQL + pgvector
 ТВ отдела продаж ────────┘              │          │  │  └──► MinIO (файлы)
                                         │          │  └─────► Redis (очереди)
                                         └► web     └► worker (фоновые задачи, outbox,
                                          (статика)    интеграции, ночной пересчёт)
 Внешние системы (СКУД, АТС, банк, касса, формы) ──webhook──► api /v1/integrations/*
 ИИ-сервер с GPU (позже) ◄──── внутренний API ──── worker
```

## 2.3. Изоляция клубов и сетей

1. В каждой рабочей таблице есть `tenant_id` (сеть), а в клубных таблицах ещё `club_id`.
2. В PostgreSQL включена построчная защита (Row Level Security): каждый запрос выполняется с параметрами текущего пользователя (сеть и список доступных клубов), и база сама не отдаёт чужие строки, даже если в коде ошибка.
3. Сотрудник видит только клубы из своих назначений. Собственник и администратор системы назначены на всю сеть.
4. Справочники платформы (например, шаблоны пресетов) хранятся без `tenant_id` и доступны только для чтения.

Так закрывается инвариант 6 ТЗ и тест AT на изоляцию клубов.

# 3. Вход и права

## 3.1. Вход по логину и паролю

| Правило | Значение |
|---|---|
| Логин | Задаёт администратор при добавлении сотрудника (латиница, цифры, точка); уникален в сети |
| Первый вход | Администратор выдаёт временный пароль, при первом входе сотрудник обязан его сменить |
| Требования к паролю | Не короче 10 символов, проверка по списку утёкших паролей, без обязательных «спецсимволов» |
| Хранение | Только хеш Argon2id, пароль нигде не хранится и не логируется |
| Защита от подбора | После 5 неудачных попыток пауза 15 минут, уведомление администратору |
| Сессия | Токен в защищённой cookie; на телефоне менеджера сессия 30 дней, в веб-кабинете 12 часов без активности |
| Сброс пароля | Делает администратор системы; сотрудник получает новый временный пароль |
| Блокировка | Заблокированный сотрудник выходит из всех сессий сразу; история и клиенты сохраняются |
| Второй фактор | Обязателен для собственника и администратора системы, а также при утверждении возвратов, скидок и расходов: код из приложения-аутентификатора (TOTP) |

## 3.2. Роли и утверждения

Роли и матрица прав из ТЗ (раздел 3) хранятся как данные, а не зашиты в код: набор разрешений на роль плюс клубы, в которых действует назначение. Лимиты утверждения хранятся в настройках сети и меняются без программиста.

| Роль | Возврат | Скидка | Расход |
|---|---|---|---|
| Менеджер ОП | — | до 5 % (по правилам акций) | — |
| Руководитель ОП | — | до 10 % | — |
| Управляющий | до 15 000 ₽ | до 15 % | до 50 000 ₽ |
| Собственник | без лимита | без лимита | без лимита |

Всё, что выше лимита роли, автоматически уходит заявкой на утверждение следующему уровню. Решение по заявке подтверждается вторым фактором и попадает в журнал аудита.

# 4. Модель продаж клуба

У клуба одно поле `sales_model`: `term` (абонементы на срок) или `subscription` (подписка). Оно определяет:

| Что зависит от модели | Абонементы на срок | Подписка |
|---|---|---|
| Категории плана | Новые клиенты, продления, возобновление бывших, персональные тренировки | Новые подписки, возврат отписавшихся, удержание, персональные тренировки |
| Воронки по умолчанию | Новые, продление, бывшие | Новые, неуспешное списание, риск отписки, отписавшиеся |
| Тарифы по умолчанию | Год, полгода, рассрочка на год | Безлимит в месяц, дневная, первый месяц со скидкой |
| Деньги | Разовая оплата или рассрочка по графику | Ежемесячное автосписание с сохранённой карты, до 3 повторных попыток |
| Ключевые показатели | Продления в срок, средневзвешенный абонемент | Регулярная выручка (MRR), отток, средняя подписка |

**Смена модели.** Администратор может сменить модель в карточке клуба. При смене:

1. действующие договоры и абонементы сохраняют свои условия до окончания;
2. новые продажи идут по новой модели;
3. категории плана и воронки текущего месяца не пересоздаются, новый набор применяется со следующего периода плана (или сразу, если администратор отметит это явно);
4. смена записывается в журнал с автором и датой (`club_sales_model_history`).

**Пресет.** При создании клуба мастер копирует готовый набор по модели: категории плана, воронки и их этапы, примеры тарифов и шаблоны договоров. Дальше клуб правит их сам.

## 5.6. Как это закрывает инварианты ТЗ

| Инвариант | Механизм |
|---|---|
| Деньги не переписываются | ledger_entries и payments без UPDATE/DELETE для приложения (права БД); исправление только сторно |
| Повторные события интеграций | Уникальные индексы на external_event_id и provider_event_id; обработчики идемпотентны |
| «Подписан» только с доказательствами | Проверка в домене contracts и ограничение в БД: статус «подписан» требует записи в signatures |
| Цена не меняет старые договоры | memberships ссылаются на price_version, версии цены неизменяемы |
| Слияние дублей без потерь | persons.merged_into_id, связи не удаляются, запись в audit_log |
| Изоляция клубов | Row Level Security по tenant_id и club_id |

# 6. Развёртывание пилота на сервере 144.31.107.204

| Вопрос | Решение |
|---|---|
| Как подключаемся | SSH по ключу с компьютера Андрея (ключ fitnes_vps), пароль не используется |
| Что ставим | Docker и Docker Compose; всё остальное в контейнерах |
| Среды | На сервере две среды: test (для проверок) и pilot (для работы клубов), разные базы и порты |
| HTTPS без домена | Пробуем выпустить сертификат Let's Encrypt на IP-адрес; если не получится, используем самоподписанный сертификат до появления домена. Без HTTPS на телефон нельзя установить PWA, поэтому домен желателен к началу пилота |
| Обновления | GitHub Actions собирает образы при каждом изменении в main и выкатывает на test; на pilot только по команде |
| Резервные копии | Ежедневная копия PostgreSQL и файлов MinIO, хранение 14 дней, копия за пределами сервера; раз в месяц проверка восстановления |
| Безопасность сервера | Вход только по ключу, закрыты все порты кроме 22, 80, 443; автообновления безопасности; fail2ban |
| 152-ФЗ | Для пилота на тестовых данных достаточно; перед загрузкой реальных клиентов нужен сервер в российском облаке с аттестацией или подтверждение, что этот сервер в РФ и подходит по модели угроз |

Минимальные требования к серверу на пилот: 4 vCPU, 8 ГБ памяти, 80 ГБ SSD. Фактические параметры проверю, как только будет подключён ключ.
