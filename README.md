# Клубная ОС — платформа управления фитнес-клубом и сетью

Собственная CRM, клубный софт и собственный серверный ИИ (Этап 1).

## Структура

- `docs/01_ТЗ_и_план/` — ТЗ (актуальная версия v2.1, прошлые в папке «архив»), последовательность разработки, шаги 1 и 3.
- `docs/02_Исходные_материалы/` — исходные пожелания и переписка рабочей группы.
- `prototype/` — кликабельный прототип экранов (шаг 2).
- `apps/api/` — сервер: Node.js + TypeScript + Fastify, PostgreSQL с построчной изоляцией клубов.
  - `db/migrations/` — схема базы, `db/scripts/` — создание базы, миграции, тестовые данные.
  - `test/` — автотесты сервера.
- `apps/web/` — веб-интерфейс (React), открывается в браузере и на телефоне.

## Что уже работает (шаг 4, каркас)

- Вход по логину и паролю, блокировка после 5 неверных попыток на 15 минут, смена временного пароля при первом входе.
- Клубы: список, мастер создания с обязательным выбором модели продаж, смена модели с записью в историю.
- Сотрудники: добавление по роли и клубу (логин создаётся сам, выдаётся временный пароль), блокировка, выдача нового пароля.
- Права по ролям; сотрудник клуба видит только свой клуб, это обеспечивает сама база данных.
- Журнал аудита всех действий, который приложение не может изменить.
- Тестовые данные: клубы «Центр» (абонементы) и «Север» (подписка), по сотруднику на роль, клиенты по категориям.

## Что работает в CRM (шаг 5)

- Лиды: ручной ввод (менеджер, РОП, ресепшн) и приём заявок по API с ключом источника; источник обязателен.
- Антидубли по телефону и e-mail во всей сети: второй клиент не создаётся, обращение добавляется к карточке.
- Назначение менеджеру с наименьшей загрузкой, задача первого ответа с нормой клуба (по умолчанию 5 минут), контроль просрочки.
- Воронки и этапы настраивает администратор (раздел «Воронки»); у новых клубов воронки создаются по модели продаж.
- Сделка в работе всегда с задачей: нельзя закрыть последнюю задачу без следующего шага, отказ только с причиной.
- Встречи (пришёл / не пришёл), карточка клиента на одной странице: контакты, сделки, этапы, задачи, обращения, история.
- Менеджер видит свои сделки и задачи, РОП и управляющий — все сделки клуба.

## Что работает в абонементах (шаг 6)

- Управляющий клуба может всё то же, что собственник, но только в своём клубе. Создавать клубы и сетевые роли могут только собственник и администратор системы.
- Раздел «Тарифы»: правила клуба (заморозка, рассрочка, закрытие прохода при долге, напоминание о продлении) и тарифы. Менять их могут собственник (в любом клубе) и управляющий (в своём).
- Значения по умолчанию: заморозка до 30 дней и до 2 раз за год абонемента, минимум 7 дней, бесплатно; рассрочка до 3 платежей раз в месяц; проход закрывается при просрочке больше 3 дней.
- Новая цена тарифа действует только для новых продаж, проданный абонемент хранит цену и условия на день покупки; история цен видна в разделе.
- В карточке клиента: продажа (сразу или в рассрочку), продление от даты окончания текущего, заморозка и разморозка с возвратом дней, расторжение с причиной, график платежей, отметка оплаты картой или наличными, причина открытого или закрытого прохода.
- Отметка оплаты временная, до подключения кассы и эквайринга (шаг 8).

## Что работает в договорах (шаг 7)

- Раздел «Договоры»: юрлицо и реквизиты клуба, загрузка PDF договора и правил клуба (с версиями). Меняют собственник и управляющий своего клуба.
- При продаже абонемента создаётся договор с номером по клубу (префикс-год-номер) и снимком реквизитов и версий документов на день продажи.
- Подписание на бумаге: «Печать» в карточке клиента, затем «Загрузить скан» (PDF, JPG, PNG).
- Подписание на планшете на ресепшн: клиент читает договор и правила, ставит отметку согласия и расписывается пальцем. Сохраняются подпись, время, устройство и хеши PDF, с которыми клиент ознакомился.
- Подписанный договор изменить нельзя, это проверяет сама база. Правило клуба «не пускать без подписанного договора» включается в «Тарифах».
- Файлы хранятся в папке `storage` в корне проекта (другую папку можно указать в `STORAGE_DIR` в `.env`).

## Касса и чеки (шаг 8)

- Раздел «Касса»: для каждого клуба собственник или управляющий выбирает режим: без кассы, облачная касса (АТОЛ Онлайн) или касса в клубе (АТОЛ автоматически через «Веб-сервер ККТ» или любая касса вручную). Там же выбирается банк эквайринга, его подключим к запуску.
- После каждой отметки оплаты создаётся чек. Облачная касса получает его с сервера, касса в клубе с компьютера ресепшн. Журнал чеков показывает ФН и ФД, ошибки и кнопку «Повторить».
- Инструкции по подключению: `docs/03_Инструкции/` (они же открываются в разделе «Касса»).
- В карточке клиента есть галочка «Списывать подписку автоматически с привязанной карты». Списания заработают с подключением банка.
- Пароль облачной кассы хранится зашифрованным ключом `FISCAL_SECRET_KEY` из `.env`.

## Финансы (шаг 8)

- Журнал платежей: каждая оплата, возврат и расход записываются один раз и не меняются.
- Кассовые смены: наличные принимаются и выдаются только при открытой смене; при закрытии касса сверяется, расхождение требует комментария.
- Возвраты: система считает рекомендуемую сумму (оплачено минус использованные дни или занятия, дни заморозки не считаются), возврат закрывает абонемент и снимает неоплаченные платежи, создаётся чек возврата.
- Согласования по лимитам: управляющий сам проводит возврат до 15 000 ₽ и расход до 50 000 ₽, сверх этого решает собственник. Решение подтверждается повторным вводом пароля, свой запрос утверждает другой сотрудник.
- Отчёты в разделе «Финансы»: ДДС за месяц, план-факт по категориям (новые, продления, возобновления, подписки), долги клиентов.

## Выгрузка предложений на сайт

- Раздел «Сайт»: управляющий готовит предложения своего клуба (можно на основе тарифа, с картинкой, старой ценой и сроком показа) и выгружает их на сайт кнопкой.
- Сайт забирает опубликованные предложения: `GET /api/public/v1/offers` с заголовком `Authorization: Bearer <ключ источника «Сайт»>`.

Приём заявок с сайта: администратор выдаёт ключ источнику (`POST /api/lead-sources/{id}/api-key`), сайт отправляет
`POST /api/v1/leads` с заголовком `Authorization: Bearer <ключ>` и полями `clubId`, `fullName`, `phone`, `comment`, `externalEventId`.

## Перенос из 1С (шаг 9)

- Раздел «Перенос из 1С»: собственник, управляющий, администратор системы, финансист.
- Пять отчётов в Excel (.xlsx) или CSV (UTF-8 или Windows-1251). Система находит строку заголовка, определяет тип отчёта и колонки с уровнем уверенности; карту подтверждает человек.
- Пробный перенос ничего не пишет в рабочие таблицы: проверяет строки, находит повторы и конфликты, строит отчёт сверки (количество, деньги по месяцам, итог 1С против суммы строк, долги, авансы, полнота).
- Перенос с паролем; до принятия его можно отменить целиком. Повторная загрузка тех же данных не создаёт дублей (таблица соответствия import_external_ids).
- Проверенные карты полей попадают в библиотеку: тот же формат у другого клуба распознаётся сразу.
- Инструкция по выгрузке: docs/03_Инструкции/Выгрузка_из_1С.md. Образцы файлов: `npm run import:samples -w apps/api -- <папка>`.

## Переписка в Telegram и WhatsApp (шаг 10)

- Раздел «Переписка»: единое окно диалогов клуба (все, непрочитанные, мои); чат и в карточке клиента. Права: messages.work (РОП, менеджер, ресепшн), настройки — messages.manage (собственник, управляющий).
- Каналы клуба («Сообщения» → «Каналы»): Telegram-бот (Bot API, приём опросом — внешний адрес не нужен), WhatsApp через Green-API (опрос), Wazzup (вебхук, после переезда на сервер), тестовый канал. Токены шифруются ключом FISCAL_SECRET_KEY.
- Новый человек пишет → карточка, заявка с меткой источника telegram/whatsapp, назначение, задача «первый ответ»; ответ менеджера закрывает её. Действующий клиент сделку не создаёт.
- Шаблоны с подстановками, автосообщения (окончание абонемента, долг, давно не был, день рождения, приветствие): один раз за повод, лимит в неделю, согласие для рекламных, отписка «СТОП», автоответ в нерабочее время.
- Фоновый обработчик (main.ts, messagingWorker) раз в 10 секунд забирает входящие и повторяет неотправленные, автосообщения проверяет раз в 10 минут. Для вебхуков задайте PUBLIC_URL.
- Инструкция: docs/03_Инструкции/Мессенджеры_Telegram_WhatsApp.md. Телефония — на финишном этапе.

## Проходы и посещения (шаг 11)

- Модель турникета выберем на финише, поэтому система работает через **шлюз** клуба (`npm run gateway` в apps/api, страница http://localhost:3100). Пока есть интернет, шлюз спрашивает решение у системы. Если связи нет, он решает сам по сохранённым правилам, копит проходы и потом выгружает их без дублей. На странице шлюза есть эмулятор турникета и режим проверки «нет интернета».
- Раздел «Проходы» состоит из трёх частей: ресепшн (лента, эмулятор, ручной проход с причиной, тревоги), отчёт (посещения, ручные проходы, отказы, приход и уход сотрудников) и настройка (часы клуба, повторный вход, шлюзы и их ключи, турникеты, карты сотрудников). Права: acs.work у ресепшн, acs.manage у управляющего и администратора.
- В карточке клиента можно выдать карту, браслет или QR, перевыпустить их без создания второго клиента и посмотреть посещения. В тарифе задаются проход по всей сети и часы прохода. Эти условия копируются в абонемент при продаже.
- Сырые события лежат в access_events (только добавление), посещения — в visits. Повторное прикладывание не засчитывается, время в клубе считается по выходу.
- Тестовые ключи шлюзов: `demo-centr-gateway-key` и `demo-sever-gateway-key`. Тестовые карты описаны в docs/03_Инструкции/Турникеты_и_шлюз.md.

## Онлайн-оплата и сверка с банком (шаг 12)

- Банк для оплаты картой и СБП выбирается в «Касса» по каждому клубу: «Тестовый банк» (встроенная проверочная страница, деньги не двигаются), ЮKassa или Т-Банк. Переход на настоящий банк — выбор банка, ключи и галочка «Боевой режим», код не меняется. Ключи хранятся зашифрованными и на экран не выводятся.
- У неоплаченного начисления есть кнопки «Ссылка» и «Ссылка в чат». После оплаты начисление закрывается само, пробивается чек, карта сохраняется для автосписания, если клиент согласен.
- Подписка продлевается сама: раз в минуту система создаёт начисление на следующий месяц и списывает деньги с сохранённой карты, при отказе повторяет по правилам клуба. Состояние ссылок система тоже проверяет сама, уведомления банка (`/api/hooks/pay/<клуб>`, нужен PUBLIC_URL) только ускоряют.
- «Финансы» → «Онлайн-оплаты» и «Сверка с банком»: загрузка выписки в формате 1С, автоматическое сопоставление эквайринга с комиссией, комиссий банка, переводов и расходов, ручной разбор остального.
- Подробно: docs/03_Инструкции/Онлайн_оплата_и_сверка_с_банком.md.

## Запуск на Windows-компьютере

Нужны Node.js 22 или новее и PostgreSQL (на компьютере уже есть Node.js 24 и PostgreSQL 18).

1. Скопировать `.env.example` в `.env` и в строке `ADMIN_DATABASE_URL` указать пароль пользователя `postgres`.
2. В папке проекта выполнить:

```
npm install
npm run db:setup
npm run db:migrate
npm run db:seed
npm run build
npm start
```

3. Открыть http://localhost:3000 и войти. Тестовые логины (пароль у всех `Fitnes-2026`):

Для разработки с автообновлением: `npm run dev` (интерфейс на http://localhost:5173).
